
# Legacy Project Validation

## Purpose

PIXIE's stewardship model applies when an older project is brought forward as much as it applies to files created today.

The validation question is not simply:

> Can we make the old thing run?

It is:

> What can we establish, preserve, rebuild, replace, measure, and safely carry forward?

## Validation lifecycle

~~~
OLD / EXISTING PROJECT
        ↓
INVENTORY
        ↓
PROVENANCE
        ↓
RIGHTS / LICENSE
        ↓
DEPENDENCY
        ↓
CURRENT-STANDARD GAP
        ↓
CONTROLLED REBUILD
        ↓
TEST / OBSERVE
        ↓
DOCUMENT
        ↓
PRODUCTION DECISION
~~~

## Paragon ReBorn as proving environment

Paragon ReBorn / Return to the Void is currently the clearest game-development example of this pattern in the PIXIE ecosystem.

Its useful role is a **controlled validation and training sandbox** where inherited or third-party material can be separated from independently built systems and evaluated against current standards.

This does not mean that the project or its assets are automatically legally cleared.

In particular:

- asset availability is not permission;
- technical reuse is not commercial permission;
- repository history is not proof of ownership;
- a prototype is not production clearance;
- a training artifact is not automatically production IP;
- a sandbox character is not automatically canonical.

## Evidence contract

Use the PIXIE evidence vocabulary:

- `DOCUMENTED` — preserved source or project record;
- `OBSERVED` — direct observation of behavior;
- `SELF-REPORTED` — participant/creator statement;
- `ATTRIBUTED` — statement tied to its speaker/source;
- `INTERPRETIVE` — analysis;
- `HYPOTHESIS` — requires testing;
- `PROPOSED` — not yet validated.

Rights, consent, provenance, and production status should be recorded separately.

## Correction as a successful outcome

The validation system should preserve corrections:

~~~
DISCOVERY
 ↓
ASSUMPTION
 ↓
VERIFICATION
 ↓
CORRECTION
 ↓
CONTROL
 ↓
RETEST
~~~

Finding a restriction before production is evidence that the control worked.

## PIXIE boundary

PIXIE can:

- surface provenance;
- explain evidence status;
- identify missing documentation;
- route a question to the appropriate reviewer;
- preserve a decision record;
- explain uncertainty.

PIXIE cannot:

- grant permission;
- determine copyright ownership;
- make a third-party license broader;
- declare a character canonical;
- convert telemetry into an unobserved claim;
- replace legal counsel or project governance.

## Cross-repository authority

- `50 Ways` provides a mature public rights/provenance case-study pattern.
- `pixie-device-stewardship` defines evidence/methodology/safety boundaries.
- `narrative-provenance` provides private provenance tooling.
- `training` provides skill development and milestone evidence.
- `Paragon ReBorn` provides a game-production validation environment.
- the receiving production repository retains authority over production acceptance and canon.
